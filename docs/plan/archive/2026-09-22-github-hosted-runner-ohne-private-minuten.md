# GitHub-hosted Runner ohne private Actions-Minuten umstellen

**Planungsstatus:** Umgesetzt
**Quelle:** `effective-flow plan`
**Empfohlener Workflow:** Feature (`effective-flow build`)

## Anforderung

Das private Repository soll auf GitHub-hosted Runner umgestellt und anschließend veröffentlicht werden, ohne dass vor der Veröffentlichung ein abrechenbarer Lauf auf einem GitHub-hosted Runner entsteht. Während des privaten Übergangs bleiben alle repository-eigenen Workflows deaktiviert; erst nach der bestätigten Public-Umschaltung und der Einrichtung der Schutzgrenzen werden sie gestuft wieder aktiviert.

Die Änderung ist ein Feature der CI/CD- und Veröffentlichungsinfrastruktur: Das Tooling-Verhalten ändert sich bewusst durch GitHub-hosted Runner, Docker-Preflight, Verify-Modus, OIDC-Publishing und neue Freigabegrenzen; Produktverhalten und öffentliche Paratix-APIs bleiben unverändert. Website, Marketing, die bestehende Lizenzstrategie und eine absichtlich ausgelöste neue npm-Version sind nicht Teil dieses Plans.

Planungsgrundlage ist `404d3d43` vom 22.09.2026. Der Arbeitsbaum enthält nur die nicht verfolgten, für diesen Plan irrelevanten Dateien `.DS_Store` und `website/.DS_Store`. Vor der Umsetzung muss der Drift der betroffenen Dateien gegenüber diesem Stand geprüft werden.

Verifizierter Kontext:

- Das GitHub-Repository `sebastian-software/paratix` ist privat. Die Workflows `CI`, `Integration Check` und `Publish` sind aktiv; Branch-Schutz beziehungsweise Rulesets und GitHub-Environments sind noch nicht verfügbar oder eingerichtet. Vorhandene Actions-Historie und -Artefakte werden mit der Sichtbarkeitsänderung ebenfalls öffentlich; aktuell sind 105 Artefakte vorhanden.
- Alle Jobs in `.github/workflows/ci.yml`, `.github/workflows/integration-check.yml` und `.github/workflows/publish.yml` verwenden derzeit `[self-hosted, linux, x64]`. Die im verwendeten API-Zugriff sichtbaren Inventarlisten enthalten aktuell keinen Runner, während frühere Jobs einen erreichbaren Self-hosted Runner in der Gruppe `Default` belegen. Verifiziert ist deshalb nur die entscheidende Schutzregel: `Default` erlaubt keine öffentlichen Repositories. Der fehlende Zugriff des öffentlichen Paratix-Repositories muss nach der Umstellung zusätzlich negativ getestet werden.
- Die repository-weite Standardberechtigung für `GITHUB_TOKEN` steht auf `write`, obwohl die bestehenden Jobs ihre Berechtigungen bereits überwiegend explizit setzen.
- `Publish` greift für release-please auf `RELEASE_PLEASE_TOKEN` zu. Der npm-Publish-Schritt verlässt sich laut Workflow-Kommentar zusätzlich auf eine persistente `~/.npmrc` des früheren Runners; ein GitHub-hosted Runner besitzt diesen Zustand nicht.
- Der Publish-Job besitzt bereits `id-token: write`, verwendet aber kein geschütztes Environment. `scripts/publishWorkspacePackages.mjs` lässt `--provenance` nur wegen der privaten Repository-Sichtbarkeit weg.
- Alle referenzierten Drittanbieter-Actions sind auf vollständige Commit-SHAs fixiert. Es gibt keine Trigger über `pull_request_target`, `workflow_run` oder `issue_comment`.
- `pull_request`-Läufe aus Forks erhalten nach GitHub-Verhalten keine Repository-Secrets und nur ein lesendes `GITHUB_TOKEN`. Standard-GitHub-hosted Runner sind für öffentliche Repositories kostenfrei. Der sichtbare dynamische Dependabot-Workflow ist kein repository-eigener Workflow, kann die Actions-Deaktivierung umgehen und verbraucht auf Standard-Runnern keine enthaltenen Actions-Minuten.
- npm Trusted Publishing kann den Herausgeber an Repository, Workflow-Datei und GitHub-Environment binden. Dafür benötigt ausschließlich der Publish-Job `id-token: write`, einen GitHub-hosted Runner und npm ab Version 11.5.1; npm empfiehlt für Release-Builds einen deaktivierten Paketcache. Bei Trusted Publishing aus einem öffentlichen GitHub-Repository erzeugt npm Provenance automatisch.
- npm 11.19.1 verweigert `npm publish --dry-run` für bereits veröffentlichte Paketversionen. Der nicht schreibende Verify-Pfad verwendet deshalb `npm pack --dry-run --json`; der separate Already-published-Release-Lauf prüft weiterhin die Registry- und Skip-Logik.
- `paratix@0.19.0` und `create-paratix@0.19.0` sind am Planungstag bereits bei npm vorhanden. Damit ist ein nicht publizierender Skip-Lauf möglich; die Registry-Versionen werden direkt vor diesem Lauf erneut geprüft.

## Architekturentscheidungen

- **Es gibt ein hartes kostenfreies Umschaltfenster.** Vor jeder Änderung an `main` werden die drei repository-eigenen Workflows und anschließend GitHub Actions auf Repository-Ebene deaktiviert; laufende beziehungsweise wartende Läufe werden beendet. Die geänderten Workflow-Dateien werden bei weiterhin privatem Repository zusammengeführt. GitHub-hosted Jobs werden erst aktiviert, nachdem GitHub die Sichtbarkeit `public` bestätigt hat.
- **Repository-eigene Jobs verwenden ausschließlich Standard-GitHub-hosted Runner.** Sämtliche `runs-on`-Angaben werden auf das stabile Image `ubuntu-24.04` umgestellt. Die Organisations-Richtlinie, dass Self-hosted Runner keine öffentlichen Repositories annehmen, bleibt als zweite Schutzschicht bestehen.
- **Unvertrauenswürdige Pull Requests erhalten keine Veröffentlichungsidentität.** CI und Integration bleiben auf `pull_request`; sie erhalten nur `contents: read`, keine Secrets und keine OIDC-Berechtigung. Im anfänglichen Public-Betrieb benötigt jeder Workflow-Lauf externer Beitragender eine Maintainer-Freigabe (`all_external_contributors`); eine spätere Lockerung erfordert eine bewusste Sicherheitsneubewertung. Zeitlimits und bestehende Concurrency-Abbrüche begrenzen Missbrauch.
- **Der Publish-Pfad wird von persistentem Runner-Zustand entkoppelt.** npm-Publishing erfolgt ausschließlich über den von npm dokumentierten Befehl `npm publish` und Trusted Publishing mit OIDC. Der Publish-Job verwendet das geschützte Environment `npm`, deaktiviert den Dependency-Cache, prüft die Mindestversion des npm-Clients und erhält automatisch Provenance. Ein `NPM_TOKEN` oder eine persistente `~/.npmrc` werden weder vorausgesetzt noch ergänzt; der bisherige `pnpm publish`-Pfad entfällt, weil seine OIDC-Unterstützung für pnpm 11 nicht als belastbare Veröffentlichungsgrenze dient.
- **Die OIDC-Vertrauensbeziehung ist eng gebunden.** Für `paratix` und `create-paratix` wird npm Trusted Publishing auf `sebastian-software/paratix`, `.github/workflows/publish.yml` und das Environment `npm` begrenzt. Das Environment lässt Deployments ausschließlich vom geschützten Branch `main` zu, verlangt eine Freigabe durch `@swernerx`, `@fastner` oder den bestehenden Organisationsbenutzer `@JamesFastnerBot` und verhindert Selbstfreigabe. Der Bot besitzt bereits Schreibzugriff auf das Repository und wurde auf ausdrückliche Operatorentscheidung als betrieblicher Ersatzreviewer ergänzt; das ist eine technische zweite Identität, aber nicht zwingend eine unabhängige menschliche Vier-Augen-Prüfung. Der Publish-Job prüft `github.ref == 'refs/heads/main'` zusätzlich im Workflow; diese Defense-in-depth ersetzt die unveränderliche Environment-Policy nicht.
- **Änderungen an der Lieferkette benötigen Code-Owner-Prüfung.** Eine neue `.github/CODEOWNERS` schützt Workflows, Publish-Skript und -Tests, Paketmanifeste, Lockfile sowie release-please-Konfiguration mit den verifizierten Administratoren `@swernerx` und `@fastner`. Das Main-Ruleset verlangt Pull Request, mindestens eine Freigabe und Code-Owner-Review sowie das Auflösen aller Diskussionen; Force-Push und Löschen bleiben gesperrt.
- **Der Notfall-Bypass bleibt im Pull-Request-Pfad.** Nur `@swernerx` und `@fastner` werden als konkrete User-Akteure mit `bypass_mode: pull_request` eingetragen. Der Modus erlaubt keinen direkten Push: Jeder Bypass bleibt im Pull Request und Audit-Log sichtbar, benötigt eine dokumentierte Notfallbegründung und wird nachträglich von der jeweils anderen Person geprüft.
- **Die Actions-Allowlist ist minimal und explizit.** Zugelassen werden GitHub-eigene Actions (`actions/*`) sowie `pnpm/action-setup` und `googleapis/release-please-action`; die Workflow-Dateien referenzieren sie weiterhin ausschließlich über vollständige Commit-SHAs. Wenn der GitHub-Plan `sha_pinning_required` nicht erzwingen kann, werden dieser fehlende Plattformzwang dokumentiert und CODEOWNERS plus Review als Ersatzkontrollen beibehalten.
- **Ein sensibler Scan-Fund löst keinen automatischen Cleanup aus.** Das Repository bleibt privat, bis ein redigiertes Inventar vorliegt und die exakten Runs, Artefakte und Credentials separat freigegeben wurden. Danach gilt zwingend die Reihenfolge Ersatz bereitstellen, Abhängigkeiten umstellen, altes Credential rotieren beziehungsweise widerrufen, freigegebene gespeicherte Daten löschen und die Nichtverwendbarkeit nachweisen.
- **Der bestehende release-please-Schlüssel wird nicht mit npm-Rechten vermischt.** `RELEASE_PLEASE_TOKEN` bleibt ausschließlich für GitHub-Schreibvorgänge von release-please zuständig. Die organisationsweite Codesuche belegt aktive Verwendungen in mindestens acht weiteren öffentlichen Repositories. Der Operator hat deshalb ausdrücklich entschieden, das Organisations-Secret weiterhin allen öffentlichen Repositories der Organisation bereitzustellen. Die dadurch verbleibende organisationsweite Vertrauensgrenze ist eine akzeptierte Restabweichung; ein npm-Token ist davon unabhängig und entfällt.
- **Der Integrationslauf darf nicht unbemerkt grün überspringen.** `Integration Check` prüft vor `pnpm agent:check:integration`, dass Docker tatsächlich erreichbar ist. Fehlt der Daemon, schlägt der Job fehl. Der lokale Skip bleibt für Entwicklungsumgebungen erhalten; der bisherige Kommentar, CI besitze generell kein Docker, wird an die neue Trennung angepasst.
- **Publish wird zuletzt aktiviert und bleibt Environment-gated aktiv.** Zuerst werden CI und Integration auf einem normalen Branch-PR verifiziert und als erforderliche Checks im Ruleset eingetragen. Erst danach werden npm-Environment, Trusted Publisher und release-please-Token geprüft und `Publish` aktiviert. Nach erfolgreichem `verify`- und Already-published-Lauf bleibt der Workflow für Release-Please aktiv; jeder echte Publish wartet auf eine fremde Environment-Freigabe. Dass OIDC bis zum ersten echten Release praktisch unbewiesen bleibt, ist eine bewusst akzeptierte Restunsicherheit ohne Token-Fallback.
- **Ein eigener Dry-run trennt Paketprüfung von Veröffentlichungsidentität.** Der manuelle Modus `verify` führt nach der normalen Validierung für beide Pakete `npm pack --dry-run --json` in einem Job ohne Environment und ohne `id-token: write` aus. Damit werden die tatsächlich gebauten Tarball-Inhalte geprüft, ohne an der bereits vergebenen Registry-Version zu scheitern. Die Modi `release` und `recover-create-paratix` bleiben dem geschützten OIDC-Job vorbehalten. Ein Already-published-Lauf prüft zusätzlich die Registry- und Release-Gates, beweist aber bewusst nicht den OIDC-Austausch.

## Implementierungsdetails

### Vorgehen

1. **Drift, Freigabe und Offenlegungsinventar prüfen.** Den aktuellen Commit, Änderungen an allen oben genannten Dateien, Workflow-Zustände, laufende oder wartende Actions-Läufe, Repository-Sichtbarkeit, Runner-Gruppen, Administratoren und aktuelle npm-Paketversionen erfassen. Die autorisierte Veröffentlichung unter dem derzeitigen MIT-Stand und die Rechtekette müssen ausdrücklich bestätigt sein; der offene Lizenzstrategieplan wird dadurch nicht stillschweigend umgesetzt. Stoppen, wenn ein weiterer Workflow Self-hosted Runner, einen Public-/Repository-Trigger oder einen Veröffentlichungsweg enthält, der in diesem Plan nicht berücksichtigt ist.
2. **Historie und bereits gespeicherte Actions-Daten vor der Öffnung prüfen.** Den vollständigen Git-Verlauf mit Gitleaks `v8.30.1`, verifizierter Release-Prüfsumme und `gitleaks git --redact --no-banner --log-opts="--all"` prüfen; ein Fund führt zu einem von null verschiedenen Exit-Code. Actions-Logs und Artefakte werden ausschließlich in ein zugriffsbeschränktes temporäres Verzeichnis außerhalb des Repositories geladen und dort auf Zugangsdaten, personenbezogene Daten und interne Infrastrukturangaben untersucht. Rohfunde werden nicht in Plan, Issues oder CI-Logs kopiert; das redigierte Beweisprotokoll enthält nur Typ, Fundstelle und Fingerprint. Temporäre Kopien werden nach Abschluss gezielt entfernt, nicht durch einen pauschalen Cleanup-Befehl. Vor jeder Löschung, Rotation oder Sperre werden exakte Run-/Artefakt-IDs, Credential-Typen, Eigentümer, Abhängigkeiten und Fingerprints read-only inventarisiert und das redigierte Beweisprotokoll außerhalb der zu löschenden Daten gesichert. Für genau diese Ziele ist eine ausdrückliche Operatorfreigabe erforderlich. Zuerst werden Ersatz-Credentials bereitgestellt und abhängige Systeme umgestellt, danach alte Credentials rotiert beziehungsweise widerrufen und erst anschließend freigegebene Runs oder Artefakte gelöscht. Nichtverwendbarkeit und Löschung werden danach verifiziert. Ohne Freigabe bleibt das Repository privat; es erfolgt keine automatische Bereinigung.
3. **Die private Actions-Grenze schließen.** `CI`, `Integration Check` und `Publish` einzeln deaktivieren und den Zustand `disabled_manually` bestätigen. Laufende oder wartende Läufe dieser Workflows abbrechen und erneut prüfen, dass keiner mehr aktiv ist. Danach GitHub Actions auf Repository-Ebene deaktivieren und diese globale Sperre zurücklesen. Den dynamischen Dependabot-Workflow nicht als Blocker behandeln: Er ist kein eigener Workflow, kann die globale Actions-Sperre umgehen und verbraucht auf Standard-Runnern keine Actions-Minuten.
4. **Workflow- und Publish-Änderungen bei deaktivierten Workflows umsetzen.** Die neun betroffenen Dateien in einem eigenen Pull Request ändern. Jede Jobdefinition muss explizit den vorgesehenen GitHub-hosted Runner und die kleinstmöglichen Berechtigungen behalten. Nur der echte Publish-Job erhält `id-token: write`; CI, Integration, Validierung und der neue Dry-run erhalten weder Secrets noch OIDC. Der Publish-Job nutzt keinen Cache und ist zusätzlich auf `refs/heads/main` begrenzt. Die CODEOWNERS-Regeln umfassen auch `.github/CODEOWNERS` selbst. Das Publish-Skript verwendet für echte Releases `npm publish` und für `verify` ausschließlich `npm pack --dry-run --json`.
5. **Lokal vollständig validieren.** `pnpm agent:check` ausführen. Danach mit erreichbarem Docker-Daemon `pnpm agent:check:integration` ausführen und anhand der Testausgabe bestätigen, dass der Block `Paratix integration` tatsächlich ausgeführt und nicht übersprungen wurde. Den neuen `verify`-Modus gegen die gebauten Artefakte ausführen und bestätigen, dass ausschließlich npm-Pack-Dry-runs entstehen. Zusätzlich die Workflow-Syntax statisch validieren und prüfen, dass nur vollständige Action-SHAs verwendet werden.
6. **Die Änderung noch privat und ohne Actions-Lauf nach `main` bringen.** Den Pull Request manuell prüfen und zusammenführen, während die drei Workflows und Repository Actions deaktiviert sind. Danach auf `main` bestätigen, dass jede eigene Jobdefinition `ubuntu-24.04` verwendet, kein eigener Workflow gelaufen ist und kein `self-hosted` mehr unter `.github/workflows/` vorkommt.
7. **Letzten Go/No-Go vor der Sichtbarkeitsänderung durchführen.** Erneut die globale Actions-Sperre, die drei deaktivierten Workflow-Zustände, leere Queue, abgeschlossenen Offenlegungsscan und erforderliche Rotationen bestätigen. Die Runner-Gruppen ausschließlich read-only prüfen: Für alle für Paratix relevanten Gruppen `allows_public_repositories` und Selected-Repository-Zugriff zurücklesen und bestätigen, dass Paratix in keiner public-fähigen Gruppe enthalten ist. Keinen Testjob mit einem Self-hosted-Label ausführen. Bleibt die API-Evidenz wegen fehlender Berechtigung unvollständig, bestätigt ein Org-Owner die Einstellung in der UI; bis dahin bleiben Actions deaktiviert und das Repository privat.
8. **Repository veröffentlichen und unmittelbar die Verwaltungsgrenzen setzen.** Die Sichtbarkeit auf `public` ändern und zurücklesen; Repository Actions bleiben dabei global deaktiviert. Danach die Actions-Standardberechtigung auf `contents: read` setzen und das Erstellen beziehungsweise Freigeben von Pull Requests durch den Standard-Token deaktivieren. Die Fork-Approvalpolicy wird auf `all_external_contributors` gesetzt, sodass jeder externe Lauf vor der Ausführung freigegeben werden muss. Zulässig sind ausschließlich `actions/*`, `pnpm/action-setup` und `googleapis/release-please-action`; vollständige SHA-Pins werden zusätzlich durch die Plattformrichtlinie erzwungen, sofern der GitHub-Plan diese Einstellung anbietet. Secret-Scanning, Push-Protection, Private Vulnerability Reporting, Dependency Alerts und automatische Security-Fixes werden aktiviert beziehungsweise bestätigt.
9. **Main zunächst ohne Publish schützen.** Ein Ruleset für `main` mit Pull-Request-Pflicht, mindestens einer Freigabe, Code-Owner-Review, veraltete Freigaben verwerfen, aufgelösten Diskussionen sowie Verbot von Force-Push und Löschen anlegen. Ausschließlich `@swernerx` und `@fastner` erhalten `bypass_mode: pull_request`; ein Einsatz nennt im Pull Request den Notfallgrund und wird nachträglich von der jeweils anderen Person geprüft. Ein Always-Bypass und direkter Push bleiben ausgeschlossen. `Publish` bleibt deaktiviert.
10. **CI und Integration gestuft aktivieren.** Repository Actions wieder aktivieren; die drei manuell deaktivierten Workflows müssen dabei deaktiviert bleiben. Zuerst `CI`, danach `Integration Check` aktivieren. Einen Test-Pull-Request mit einer harmlosen Änderung öffnen beziehungsweise aktualisieren. Beide Jobs müssen auf `ubuntu-24.04` erfolgreich laufen; der Integration-Log muss einen erfolgreichen Docker-Preflight und tatsächlich ausgeführte Paratix-Integrationstests zeigen. Danach die aus der API zurückgelesenen Check-Kontexte – erwartet werden `check` und `integration-check` – samt GitHub-Actions-App-ID als erforderliche Checks in das Main-Ruleset aufnehmen. Ein zweiter kleiner Pull Request muss anschließend beweisen, dass beide Gates tatsächlich ausstehen und einen Merge bis zum Erfolg blockieren.
11. **Veröffentlichungsidentitäten einrichten.** Das GitHub-Environment `npm` so konfigurieren, dass ausschließlich der geschützte Branch `main` deployen darf, `@swernerx`, `@fastner` und `@JamesFastnerBot` als Reviewer eingetragen sind und Selbstfreigabe verhindert wird. Branch-Policy und Reviewer-Konfiguration über API beziehungsweise UI zurücklesen. Für beide npm-Pakete Trusted Publishing mit Repository `sebastian-software/paratix`, Workflow `publish.yml`, Environment `npm` und direktem Publish-Recht einrichten und die Konfiguration zurücklesen. Die aktive Verwendung von `RELEASE_PLEASE_TOKEN` in anderen Organisations-Repositories dokumentieren und das Secret gemäß Operatorentscheidung unverändert für öffentliche Organisations-Repositories verfügbar lassen; niemals seinen Wert protokollieren.
12. **Publish zuletzt aktivieren und zweistufig proben.** Zuerst `Publish` aktivieren und den unprivilegierten Modus `verify` ausführen; Validate, Artefakttransfer und beide npm-Pack-Dry-runs müssen erfolgreich sein, ohne OIDC- oder Environment-Freigabe. Danach über die Registry erneut bestätigen, dass beide Manifestversionen bereits veröffentlicht sind, und den Modus `release` manuell starten. Der geschützte Job muss die Mindestversion von npm bestätigen und beide Pakete als bereits veröffentlicht erkennen, sodass kein echter `npm publish` erfolgt. Fehlt eine Version oder weichen die Versionen ab, wird der Release-Lauf nicht gestartet und `Publish` bleibt deaktiviert, bis ein bewusst geplanter Release vorliegt.
13. **Abschlusszustand festhalten.** Bestätigen, dass alle repository-eigenen Jobs Standard-GitHub-hosted Runner verwenden, die read-only Runner-Gruppen-Evidenz einen Self-hosted Zugriff für Paratix ausschließt, die drei Workflows aktiv sind und die erforderlichen Checks greifen. `Publish` bleibt aktiv, aber jeder echte Publish wird bis zur fremden Environment-Freigabe gesperrt. Der erste echte npm-Release bleibt ein überwachter Betriebsschritt: Environment-Freigabe erteilen, OIDC-Erfolg prüfen und anschließend die automatisch erzeugte Provenance-Attestation beider Pakete in npm kontrollieren.

### Randfälle

- Wird durch die Sichtbarkeitsänderung unerwartet ein eigener Workflow aktiviert oder eingereiht, wird er sofort abgebrochen und der betroffene Workflow wieder deaktiviert. Die Veröffentlichung wird nicht durch erneutes Aktivieren anderer Workflows „repariert“.
- Liefert der History-/Log-/Artefakt-Scan einen nicht sicher entkräfteten Befund, bleibt das Repository privat. Ohne exakte Ziele und ausdrückliche Operatorfreigabe wird nichts gelöscht oder rotiert. Löschen allein genügt bei Credentials nicht; nach der Freigabe werden zuerst Abhängigkeiten auf Ersatz-Credentials umgestellt und möglicherweise offengelegte Schlüssel anschließend rotiert oder widerrufen.
- Das Aktivieren eines Workflows spielt während der Deaktivierung verpasste Ereignisse nicht nach. Der Test-Pull-Request muss nach der Aktivierung geöffnet oder durch einen neuen Commit beziehungsweise erneutes Öffnen aktualisiert werden.
- Ein öffentlicher Fork kann in CI absichtlich beliebigen Repository-Code und Install-Skripte ausführen. Die Sicherheitsgrenze ist deshalb der ephemere GitHub-hosted Runner ohne Secrets, OIDC oder schreibenden Token – nicht die Vertrauenswürdigkeit des Codes. Netzwerk- und Rechenmissbrauch bleiben innerhalb von Freigabe, Zeitlimit und Concurrency als Restoberfläche bestehen.
- Caches und Artefakte aus unvertrauenswürdigen Läufen gelten als nicht vertrauenswürdig. Der Publish-Job verwendet keinen Dependency-Cache und übernimmt ausschließlich das Artefakt seines eigenen, auf `main` laufenden Validate-Jobs.
- Schlägt der Docker-Preflight auf `ubuntu-24.04` fehl, darf die Integration nicht durch einen Skip als erfolgreich gelten. Der Workflow bleibt deaktiviert beziehungsweise nicht erforderlich, bis Runner-Image oder Testaufbau bewusst angepasst wurden.
- Kann das Environment `npm` keine voneinander unabhängige Freigabe erzwingen, wird Publish nicht aktiviert. Dasselbe gilt, wenn npm die Bindung an Repository, Workflow und Environment nicht zurückliefert.
- Sind die aktuellen Paketversionen noch nicht veröffentlicht, ist der manuelle Publish-Lauf kein Test mehr, sondern ein irreversibler Release. Er wird dann separat entschieden und nicht im Rahmen der Runner-Umstellung ausgelöst.
- Erreicht `npm publish` beim ersten echten Release die Trusted-Publishing-Identität mit dem verwendeten npm-Client nicht oder weichen Repository, Workflow-Datei beziehungsweise Environment von der npm-Konfiguration ab, wird der Lauf abgebrochen und `Publish` sofort wieder deaktiviert. Es gibt keinen Fallback auf Runner-Dateien oder ein npm-Token.
- Das Zurückschalten auf `private` ist kein normaler Rollback, weil Sichtbarkeitsänderungen bereits erfolgte Forks, Klone oder Offenlegung nicht zurückholen. Vor dem Public-Schritt ist der Rollback schlicht „privat und deaktiviert bleiben“; danach besteht der sichere Rollback darin, Workflows wieder zu deaktivieren und Publish gesperrt zu lassen.

## Akzeptanzkriterien

Die Umstellung ist genau dann abgeschlossen, wenn ein gemeinsames Abnahmeprotokoll alle folgenden Nachweise enthält:

- [x] Für den Zeitraum vom bestätigten globalen Deaktivieren von Repository Actions bis zur bestätigten Public-Sichtbarkeit weist die Actions-Laufliste keinen repository-eigenen Lauf auf einem GitHub-hosted Runner und die Abrechnung keine entsprechende private Nutzung aus; damit sind für die Umschaltung keine privaten GitHub-Minuten angefallen.

- [x] `.github/workflows/` enthält weder `self-hosted` noch einen nicht berücksichtigten privilegierten Trigger; alle externen Actions bleiben auf vollständige Commit-SHAs fixiert.
- [x] Ein nach der Veröffentlichung erzeugter Test-Pull-Request hat die aus der API ermittelten Check-Kontexte – erwartet `check` und `integration-check` – auf Standard-GitHub-hosted Runnern erfolgreich durchlaufen; der Integration-Log belegt erreichbares Docker und ausgeführte statt übersprungene Paratix-Integrationstests.
- [x] Das Main-Ruleset erzwingt Pull Request, mindestens eine Freigabe, Code-Owner-Review, aufgelöste Diskussionen und beide erfolgreichen Checks; Force-Push und Branch-Löschung sind gesperrt.
- [x] Der Ruleset-Bypass nennt ausschließlich `@swernerx` und `@fastner` als User-Akteure mit `bypass_mode: pull_request`; ein Test in der Ruleset-Vorschau beziehungsweise API-Ausgabe belegt, dass kein Always-Bypass und kein direkter Push zugelassen sind. Notfalleinsätze müssen begründet und von der jeweils anderen Person nachträglich geprüft werden.
- [x] Die Fork-Approvalpolicy steht auf `all_external_contributors`; jeder externe Lauf benötigt vor der Ausführung eine Maintainer-Freigabe, erhält keine Repository-Secrets und besitzt weder schreibendes `GITHUB_TOKEN` noch `id-token: write`. Die repository-weite Standardberechtigung ist lesend und die Allowlist enthält ausschließlich `actions/*`, `pnpm/action-setup` und `googleapis/release-please-action`. Alle Workflow-Referenzen bleiben auf vollständige SHAs gepinnt; ein nicht verfügbarer Plattformzwang ist als Restabweichung dokumentiert.
- [x] Das Environment `npm` lässt ausschließlich Deployments vom geschützten Branch `main` zu, verhindert Selbstfreigabe und verlangt eine Freigabe durch `@swernerx`, `@fastner` oder `@JamesFastnerBot`; der Workflow begrenzt den Publish-Job zusätzlich auf `refs/heads/main`. npm bestätigt für `paratix` und `create-paratix` die Bindung an Repository, `publish.yml`, dieses Environment und direktes Publish-Recht. Die geringere personelle Unabhängigkeit einer Bot-Freigabe ist als bewusste Restabweichung dokumentiert.
- [x] Die organisationsweite Verwendung von `RELEASE_PLEASE_TOKEN` ist dokumentiert. Das Secret bleibt auf ausdrückliche Operatorentscheidung für alle öffentlichen Organisations-Repositories verfügbar; diese breitere Vertrauensgrenze ist als Restabweichung akzeptiert und wird nicht als repository-spezifische Absicherung dargestellt.
- [x] Der unprivilegierte `verify`-Lauf hat die Tarball-Inhalte beider Pakete ausschließlich per `npm pack --dry-run --json` geprüft; der kontrollierte `release`-Lauf hat bei bereits vorhandenen Versionen keinen echten Publish-Aufruf ausgeführt. Für den ersten späteren echten OIDC-Release ist die Prüfung der automatisch erzeugten Provenance als verpflichtender Betriebsschritt festgehalten.
- [x] Die read-only API-/UI-Evidenz belegt ohne Self-hosted-Testdispatch, dass Paratix in keiner public-fähigen Runner-Gruppe enthalten ist; die drei eigenen Workflows sind nach der gestuften Freigabe aktiv, während jeder echte Publish eine fremde Environment-Freigabe benötigt, und alle übrigen Veröffentlichungssperren sind dokumentiert.

## Validierungsplan

- Vor und nach jedem Zustandswechsel die GitHub-API für Repository-Sichtbarkeit, Workflow-Zustände, laufende/queued Runs, Actions-Standardberechtigungen, Environment-Reviewer und -Deployment-Branch-Policy, Ruleset und Runner-Zugriff abfragen. Erwartet werden ausschließlich die im Vorgehen genannten Zustände.
- `pnpm agent:check` lokal ausführen; erwartet wird Exit-Code 0.
- `pnpm agent:check:integration` lokal mit aktivem Docker ausführen; erwartet werden Exit-Code 0 und tatsächlich ausgeführte Tests des Blocks `Paratix integration`.
- Den geänderten Publish-Skript-Test gezielt und anschließend über `pnpm agent:check` ausführen. Die erwarteten echten Aufrufe müssen direkt `npm publish` verwenden; `verify` muss nur `npm pack --dry-run --json` erzeugen, während der Already-published-Fall weiterhin keinen echten Publish-Prozess startet.
- Die drei Workflow-Dateien lokal mit `pnpm exec prettier --check .github/workflows` syntaktisch parsen; erwartet wird Exit-Code 0. Zusätzlich nach `self-hosted`, nicht fixierten `uses:`-Referenzen, `pull_request_target`, `workflow_run`, `issue_comment`, unerwartetem `id-token: write` und Secret-Zugriffen außerhalb des vorgesehenen Jobs suchen. Da im Repository kein semantischer Actions-Validator etabliert ist, bilden die beiden Hosted-Canary-Pull-Requests die verbindliche semantische Workflow- und Ruleset-Validierung.
- Nach der Veröffentlichung einen normalen Pull Request ausführen. Die Check-Suite muss die erwarteten Namen erzeugen, damit genau diese Namen ins Ruleset übernommen werden können.
- Optional mit einem Test-Fork verifizieren, dass GitHub vor dem Lauf eine Freigabe verlangt und im Lauf keine Secrets vorhanden sind. Es werden keine Secret-Werte ausgegeben; geprüft werden nur Vorhandensein beziehungsweise Abwesenheit der erwarteten Variablennamen und Token-Berechtigungen.
- Vor dem Publish-Probelauf die Versionen aus beiden `package.json` gegen npm prüfen. Erwartet wird, dass beide exakt vorhanden sind. Im `verify`-Log sind ausschließlich mit `--dry-run` versehene Pack-Aufrufe zulässig; im anschließenden `release`-Log müssen beide Skip-Meldungen erscheinen und jeder echte Publish-Aufruf ist ein Abbruchkriterium.
- Beim ersten echten Release die npm-Paketansichten auf Provenance und die GitHub-Deployment-Historie auf die erforderliche Environment-Freigabe prüfen.
